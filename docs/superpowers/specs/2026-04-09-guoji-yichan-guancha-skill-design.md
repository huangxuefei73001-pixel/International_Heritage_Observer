# 国际遗产观察 Skill 设计说明

## 1. 背景与目标

本项目旨在将公众号“国际遗产观察”的既有文章库整理为一个可被 Codex 调用的专业研究 skill，服务于遗产保护、文博、规划等领域的工作与研究场景。

第一阶段的核心目标不是做一个开放式百科问答助手，而是做一个“库内作证”的研究助手：

- 能从“国际遗产观察”文章库中检索、归纳并回答问题
- 能为结论提供可追溯的文章证据和原文链接
- 能支持写报告、做综述、找案例、查概念、追动态等真实工作场景
- 在证据不足时明确说明边界，而不是补充库外常识

## 2. 第一阶段边界

第一阶段必须遵守以下边界：

- 默认只使用“国际遗产观察”本地文章库回答问题
- 不将通用常识、模型预训练知识或外部网页信息混入回答
- 找不到直接证据时，明确说“当前库内没有足够材料支持该回答”
- 允许对多篇文章进行有限归纳，但必须标注“基于库内文章归纳”

第一阶段暂不包含：

- 开放式百科问答
- 自动混合外部资料的回答
- 静默自动补库后直接上线
- 复杂的语义检索或大规模向量数据库方案

## 3. 用户场景

用户提问不会被限制为固定模板。skill 应允许自然、发散、工作化的提问方式，例如：

- 查概念或背景：“奥胡斯公约是什么”“突出普遍价值怎么界定”
- 查动态：“最近韩国有什么世界遗产动态”
- 找案例：“找几个欧洲近年关于过度旅游治理的案例”
- 写报告：“帮我整理一段能放进汇报的国际趋势概述，附出处”
- 做研究：“国际上近年关于遗产数字化和 AI 修复有哪些讨论线索”

因此，固定的是内部证据工作流，而不是用户提问格式。

## 4. 总体设计

整体采用三层结构：

1. 原始层：保留现有公众号文章抓取文件，作为不可覆盖的原始材料。
2. 整理层：将文章解析为统一结构的本地知识记录。
3. Skill 层：skill 仅基于整理后的结构化知识库完成检索、归纳和作答。

这样设计的目的是将“原始材料保存”和“对外回答逻辑”解耦，便于后续增量补库、字段修正和能力扩展。

- 若正文标题缺失或为 `(unknown)`，回退使用文件名作为标题

## 6. 结构化知识库设计

每篇文章整理后至少应包含以下字段：

- `id`：本地唯一标识
- `title`：文章标题
- `published_at`：发布时间
- `channel`：固定为“国际遗产观察”
- `category`：原目录分类，如 `韩国`、`欧洲`、`UNESCO`
- `source_url`：公众号原文链接
- `local_source_path`：原始文件绝对路径
- `content_text`：清洗后的正文文本
- `content_html_excerpt`：必要时保留的 HTML 片段，便于后续改进解析
- `parse_status`：解析状态，如 `ok`、`title_fallback`、`needs_review`
- `tags_auto`：后续可自动补充的主题标签

第一阶段建议采用简单、透明、易审阅的本地格式，例如：

- 每篇一份 JSON
- 或单篇 Markdown 搭配 YAML frontmatter

只要满足“稳定检索、易复核、易增量补入”即可。

## 7. Skill 的内部工作流

用户提问进入 skill 后，不要求具备固定格式。skill 内部需先完成问题归一化，再执行检索和回答。

内部归一化维度包括：

- 对象：国家、城市、机构、遗产地、概念、会议、项目
- 主题：申遗、管理规划、影响评估、过度旅游、气候变化、数字化、阐释展示等
- 时间：最近、某一年、近几年、某届大会前后
- 任务类型：概念解释、动态追踪、案例收集、研究综述、写作辅助
- 输出强度：简答、证据清单、报告段落、综述摘要

skill 的基本流程为：

1. 判断用户的问题属于哪种工作任务
2. 将问题拆解为可检索维度
3. 在结构化库内检索相关文章
4. 判断证据是否足够支撑回答
5. 用“结论 + 证据”的格式组织输出
6. 在必要时提示证据边界

## 8. 回答规则

第一阶段回答应尽量保持研究助手风格，而非百科风格。

默认输出结构建议为：

### 8.1 问题理解

将用户问题转写为当前回答采用的检索理解，便于用户确认范围。

### 8.2 库内结论

先给简明结论，但必须明确说明：

- 这是基于库内文章整理得出的结论
- 不是对库外世界的全面判断

### 8.3 证据文章

列出 3 至 5 篇最相关的文章。每条应尽量包括：

- 标题
- 日期
- 分类
- 原文链接
- 与问题的相关点

### 8.4 可直接用于写作的归纳

给出 2 至 4 条可直接改写进报告、汇报、研究笔记的简短归纳句。

### 8.5 证据边界

如果库内材料不足、时间范围不完整、证据只覆盖单一角度，必须主动提示。

## 9. 拒答与降级规则

为了保证准确性，第一阶段应明确以下行为：

- 纯常识问题若库内无直接支撑，不作开放回答
- 只找到单篇边缘材料时，不做强归纳
- 多篇文章观点不一致时，优先并列呈现，而不是强行统一
- 时间范围不明确时，可做合理收缩，但应写明实际使用的时间范围
- 若用户请求超出当前库覆盖范围，应说明“当前库内暂缺足够材料”

## 10. 检索策略

第一阶段优先采用稳定、可解释的检索方式，不预设复杂的语义检索。

建议优先组合：

- 标题关键词检索
- 分类目录过滤
- 发布时间过滤
- 正文关键词检索
- 可选的主题标签检索

检索结果的排序原则优先考虑：

- 与问题对象的直接相关性
- 时间匹配程度
- 与问题主题的匹配程度
- 是否可作为直接证据引用

## 11. 增量更新设计

增量更新建议采用“两阶段”策略。

### 11.1 阶段 A：半自动补库

先做人工触发的补库流程：

- 从公众号下载 API 或导出功能获取新增文章列表
- 只处理库内不存在的文章
- 解析为与历史文章一致的结构化记录
- 写入前做去重和字段校验
- 输出同步日志

阶段 A 的目标是验证：

- 新文章发现是否稳定
- 解析质量是否稳定
- 去重逻辑是否可靠
- 入库后回答质量是否稳定

### 11.2 阶段 B：定期自动同步

待半自动流程稳定后，再增加定时运行：

- 每天或每周执行一次
- 只补增量
- 失败不覆盖旧数据
- 保留每次同步日志和异常记录

默认原则是：

- 宁可漏收一篇，也不要误收错误内容
- 解析异常文章进入待复核状态，而不直接进入主库

## 12. API 方案

用户已提出使用 mptext 体系作为公众号文章增量获取入口。

当前已确认的事实包括：

- `docs.mptext.top` 提供 API 使用说明
- API 使用 `X-Auth-Key` 鉴权
- 官方教程提供公众号文章链接批量导出方案

第一阶段建议将其作为“新增文章发现”入口，而不是立即假设其能无损提供所有正文能力。实现时应先确认：

- 是否可稳定获取文章链接
- 是否可获取发布时间和标题等元数据
- 是否可直接获取正文
- 若不能直接获取正文，是否可将其作为增量发现层，再由本地解析流程补正文

## 13. 第一阶段成功标准

第一阶段完成后，应达到以下效果：

- 用户可以自然提问，而无需背诵固定模板
- skill 能在库内检索出相关证据文章
- 回答中能区分“结论”和“证据”
- 回答可直接为报告或研究笔记提供材料
- 证据不足时不会假装知道
- 后续可在不推翻结构的前提下接入新增文章补库能力

## 14. 非目标

以下内容不属于第一阶段目标：

- 自动混合外部互联网资料
- 通用遗产知识百科能力
- 完整的 RAG 平台化系统
- 高复杂度多模态处理
- 自动替代人工学术判断

## 15. 推荐实施顺序

建议按以下顺序实施：

1. 确定结构化库格式
2. 完成原始文章解析与整理
3. 完成 skill 的检索与回答规则
4. 用真实问题压测回答质量
5. 实现手动触发的增量补库
6. 稳定后再增加定时同步

## 16. 当前结论

本项目第一阶段应优先交付一个“库内优先、证据导向、支持自然提问”的研究型 skill，而不是一次性追求全自动抓取与开放式问答。

只有先把知识边界、引用规则、结构化库和回答逻辑做稳，后续的增量更新、常识补充和研究能力扩展才不会破坏其可信度。
