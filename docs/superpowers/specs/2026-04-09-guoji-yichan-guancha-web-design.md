# 国际遗产观察 Web 第一版设计说明

## 1. 目标

本项目的目标，是把已经验证有效的“国际遗产观察”本地知识库问答能力，包装成一个普通用户可直接使用的网页产品，并部署到腾讯云轻量服务器上。

这一版的重点不是做完整平台，而是尽快交付一个可被少量真实用户使用的网页研究助手：

- 普通用户无需编码即可提问
- 回答继续保持“库内优先、证据导向”
- 网站记录每位用户自己的上下文会话
- 管理员可以查看全部对话，并手动更新知识库
- 后续若使用者增多，再扩展邀请制和更复杂的权限模型

## 2. 第一版边界

第一版只做最小可用版本，优先保证：

- 网页可用
- 问答可用
- 上下文可保存
- 管理员可更新库
- 整体能稳定部署在单台腾讯云轻量服务器

第一版明确包含：

- 邮箱验证码登录
- 普通用户聊天页
- 普通用户“我的会话”
- 管理员查看全部对话
- 管理员手动触发知识库更新
- 严格库内优先回答
- OpenRouter 作为模型上游

第一版明确不包含：

- 邀请码 / 邀请制门槛
- 企业微信接入
- 自动定时抓取公众号
- 多租户
- 用户自定义知识库
- 复杂后台
- 向量数据库或复杂 RAG 基础设施

## 3. 角色设计

系统只区分两种角色：

### 3.1 普通用户

登录后只看到：

- 聊天页
- 我的会话

普通用户不能看到：

- 管理员后台
- 其他用户会话
- 知识库更新入口

### 3.2 管理员

登录后直接进入管理员后台，只看到：

- 全部对话
- 知识库更新

管理员第一版不需要进入普通用户界面，也不和普通用户共用同一套导航。

## 4. 页面结构

第一版页面收敛为 3 个核心页面：

### 4.1 登录页

- 邮箱输入
- 验证码发送
- 验证码登录

### 4.2 用户侧

包含两块核心区域：

- 我的会话列表
- 聊天页

聊天页中的回答只保留 3 块：

- 简明回答
- 证据文章
- 边界提示

证据文章标题应为可点击链接，可直接打开原文。

### 4.3 管理员侧

管理员页只保留两块：

- 全部对话
- 手动更新知识库

“手动更新知识库”第一版只需要一个清晰动作：

- 点击按钮后触发“分类并更新入库”
- 页面显示最近一次更新结果和同步日志

## 5. 回答规则

网页产品继续沿用当前 skill 的核心规则：

- 默认严格库内优先
- 不混入开放常识
- 基于库内文章做有限归纳
- 证据不足时明确提示不足

回答结构统一为：

1. 简明回答
2. 证据文章
3. 边界提示

网页第一版不需要完整展示 skill 里的全部中间结构，如“问题理解”或“可直接用于写作的归纳”，以免界面过重。后续如有需要，再增加“展开更多”。

## 6. 上下文设计

网页需要记录所有使用者的上下文对话，但第一版只做最小实现：

- 每个用户有自己的会话列表
- 每条会话保存连续消息
- 回答时读取当前会话最近若干条消息作为上下文
- 不做无限长上下文拼接

第一版上下文原则：

- 每个用户的会话彼此隔离
- 管理员可查看全部会话
- 普通用户只看到自己的会话

## 7. 数据结构

第一版数据库只保留最小核心表：

### 7.1 users

- id
- email
- role
- created_at
- last_login_at

### 7.2 conversations

- id
- user_id
- title
- created_at
- updated_at

### 7.3 messages

- id
- conversation_id
- role
- content
- sources_json
- created_at

### 7.4 login_codes

- id
- email
- code_hash
- expires_at
- used_at

不在第一版保留复杂邀请表。未来若启用邀请制，再补 `invites` 表即可。

## 8. 技术架构

第一版采用轻量单体架构：

- 前端：Next.js
- 后端：FastAPI
- 数据库：PostgreSQL
- 反向代理：Nginx
- 模型上游：OpenRouter
- 知识库：本地 `articles.jsonl`

设计原则是：

- 不重写现有知识引擎
- 最大程度复用现有 Python 查询与补库逻辑
- 不为了“像平台”而做过度拆分

## 9. 知识库更新机制

当前本地更新流程已经存在：

- 新文章进入 `本次新增`
- 分类
- 更新入库
- 重建知识库

网页第一版直接复用这一流程。

管理员点击后台按钮后，后端应触发：

1. 对新增文章执行分类
2. 重建本地结构化库
3. 写入同步日志
4. 将结果反馈到后台界面

网页回答时始终读取当前最新的本地知识库，因此：

- 库更新后，网页无需单独改动即可使用最新内容

## 10. 视觉方向

第一版网页风格采用：

- 深蓝色主基调
- 山野气质
- 麦理浩径风格

视觉上应避免：

- 泛 AI 聊天工具模板感
- 过于拥挤的信息密度
- 重科技感紫色渐变
- 后台式深色控制台压迫感

建议氛围关键词：

- 夜色
- 山脊
- 路径
- 雾气
- 研究笔记
- 安静、克制、耐看

同时，用户已经明确要求：

- 页面留白更多
- 界面更透气
- 在山野深蓝氛围中保持轻盈

## 11. 部署方案

第一版部署在腾讯云轻量服务器上。

推荐部署形态：

- Nginx 对外提供统一入口
- Next.js 前端服务
- FastAPI 后端服务
- PostgreSQL 本机部署
- 项目代码、本地知识库、本地同步日志都放在服务器上

第一版允许：

- 单机部署
- 少量用户使用
- 以快速上线为目标

第一版不要求：

- 微服务
- 托管数据库
- 自动扩容
- 高可用集群

## 12. 成功标准

第一版完成后，应达到以下效果：

- 用户可以通过网页登录并提问
- 系统能连续记录用户自己的历史会话
- 回答基于“国际遗产观察”知识库，且附证据链接
- 管理员能查看全部对话
- 管理员能通过后台更新知识库
- 知识库更新后，网页回答自动读到最新库
- 整体可稳定运行在腾讯云轻量服务器

## 13. 后续扩展预留

本设计刻意为未来保留扩展空间，但不纳入第一版实现：

- 邀请制 / 邀请码
- 企业微信 bot 接入
- 自动定时抓取
- 更复杂的管理后台
- 多模型支持
- 更多角色权限
- 向量检索或混合检索升级

## 14. 结论

“国际遗产观察”网页第一版应优先被做成一个轻量、克制、可上线的研究助手，而不是平台化大工程。

核心原则是：

- 复用已验证有效的本地知识库能力
- 保持库内优先与证据导向
- 用最小网页产品包装已有价值
- 给后续邀请制、团队共享和企业微信接入留出升级路径
